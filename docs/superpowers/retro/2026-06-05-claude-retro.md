## 名詞速查表（新人先看這個）

讀到不懂的詞先回來查這張表，每個只用一句話講白：

| 詞                                  | 白話意思                                                                                                                          |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **預渲染 / prerender**              | 部署前就把每頁的 HTML 和資料一起「烤」成靜態檔案。使用者一打開就是成品，不用等瀏覽器再去要資料。                                  |
| **payload**                         | 預渲染時連同 HTML 一起送到瀏覽器的那包資料。                                                                                      |
| **chunk**                           | 打包後切出來的一塊 JavaScript 檔。                                                                                                |
| **code-split / 動態 import()**      | 把一大塊程式拆成好幾個 chunk，需要時才載入，首頁就不用一次載完。                                                                  |
| **canvas**                          | HTML 的一張「畫布」，可以用程式在上面直接畫圖（像畫在一張紙上）。                                                                 |
| **DOM marker**                      | 地圖上每個 pin 都是一個獨立的網頁元素（DOM node）。數量一多，瀏覽器很吃力。                                                       |
| **合成層 / compositing layer**      | 瀏覽器把畫面拆成很多張圖層各自畫、再疊起來。圖層越多，弱機 GPU 越累。把 109 個 DOM marker 改畫到 2 張 canvas，要疊的層就剩 2 張。 |
| **重投影 / reproject**              | 地圖縮放（zoom）時，要把經緯度重新換算成螢幕座標。點越多越慢——這就是 352ms→74ms 在量的那件事（同一台弱機、同樣放大操作）。        |
| **Douglas-Peucker（DP）簡化**       | 一種演算法，把一條線上「幾乎在直線上」的點刪掉，形狀看起來不變但點數大減（174k→10k）。                                            |
| **vector tiles / MapLibre GL**      | 用顯示卡（WebGL）畫地圖的新一代工具，比 Leaflet 更快、更像 Google 地圖。                                                          |
| **dev-gated / `import.meta.dev`**   | 用「只在開發時執行」的開關包住的程式；正式上線（production）會被拿掉，使用者看不到。                                              |
| **design token（raw vs semantic）** | 設計用的變數。raw＝原始色票（如某個橘色）；semantic＝語意別名（如「主要強調色」指向那個橘）。改一個別名，全站跟著變。             |
| **worktree**                        | 同一個 git repo 另外開的一份獨立工作目錄，讓不同功能互不干擾。                                                                    |
| **atomic commit（原子提交）**       | 每個「驗證過、沒壞」的小改動就 commit 一次，方便日後一步步回溯。                                                                  |
| **GTFS / OSM**                      | 兩種地圖/交通開放資料來源。GTFS＝大眾運輸時刻表標準；OSM＝OpenStreetMap 開放街圖。                                                |
| **GSD**                             | 一套「先討論 → 規劃 → 執行」的工作流方法；術語（phase/roadmap）對 Tony 全程翻成白話。                                             |
| **background-first**                | 非即時的實作一律丟背景跑，主對話永遠不卡住。                                                                                      |
| **偷吃步**                          | 為了讓畫面/測試看起來對，去遮症狀而不修真正的 bug。本專案明令禁止。                                                               |
| **技術債**                          | 為了趕快交付而留下、之後得回頭還的爛攤子（將就的程式）。                                                                          |

## 3. 技術決策對標 2026 最佳實踐

> 註：原本用 `/deep-research` 跑多來源查證，搜尋與抓取都成功（Nuxt v4 docs、jawg「MapLibre GL vs Leaflet」、Tailwind v4 blog、pkgpulse「Maps 2026」），但 harness 最後的 synthesize 步驟掛掉（subagent 沒回傳結構化結果，是工具 bug 不是內容問題）。下方判定改由既有 2026 知識 + 研究抓到的來源 + architect 證據綜合而成；要正式引用可重跑研究。
>
> 圖例：✅ 最佳實踐 ｜ 🟡 可接受（非最佳，有更好選項）

| #   | 決策                                                                                  | 判定 | 依據                                                                                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **全站預渲染 + 禁用 `useLazyAsyncData`，一律 `useAsyncData`**                         | ✅   | 預渲染路由的資料會被烤進靜態 HTML payload，頁面一載入就有資料。`useLazyAsyncData` 只有在「頁面不預渲染、想讓外殼先畫、資料晚點到」時才有用——本站沒有這情境。全站禁用（保留一個有記載的例外）正確。                                                                                                                     |
| 2   | **Leaflet `preferCanvas` + Douglas-Peucker 簡化 + 互動時凍結動畫**（174.8k 頂點邊界） | 🟡   | 對「不填色的邊界外框」這種靜態向量，canvas + DP 簡化是合法、低風險的修法，實測 4.8×。但這個頂點量級的**教科書最佳解是 vector tiles + MapLibre GL（WebGL）**。團隊已正確指出更深的成本是 retina @2x raster 底圖，並把 MapLibre GL 留成 dev-gated 選項。所以現在可接受；若弱機載入/手感仍差，升級 MapLibre GL 是既定路。 |
| 3   | **`useLazyAsyncData` + 動態 `import()` 把大餐廳資料集擠出路由 chunk**（唯一例外）     | 🟡   | 動態 `import()` 是 Vite/Rollup 慣用的 code-split 邊界，正是把大資料集擋在初始 chunk 外的對的工具。這個 lazy 有理由、有註解、有記載。（純預渲染的替代是另開一個 fetched JSON payload，但動態 import 更簡單、夠好。）                                                                                                    |
| 4   | **Tailwind v4 `@theme`：raw token + 語意別名兩層**                                    | ✅   | 「原始 token（`@theme`）→ 語意別名」的兩層架構正是 Tailwind v4 推薦寫法；brand token 以 utility 形式露出也是慣用法。                                                                                                                                                                                                   |
| 5   | **獨立 `@storybook/vue3-vite`（不用 `@nuxtjs/storybook`）**                           | 🟡   | 由有記載的 rolldown/vite-plus 工具鏈衝突證成（`@nuxtjs/storybook` 假設標準 Nuxt/vite 鏈）。代價是 story 裡少了 Nuxt 自動匯入糖（已用把設定折進 `@nuxt/ui/vite` 緩解）。可接受；待 `@nuxtjs/storybook` 支援 rolldown 再回頭看。                                                                                         |
| 6   | **Cloudflare 清理用分頁 REST API，不用 wrangler 列部署**                              | ✅   | `wrangler pages deployment list` 只回傳近期/上限切片、不分頁完整歷史，所以「列出來清理」必須打 REST API 分頁。判斷正確。                                                                                                                                                                                               |

**一句總結**：六個決策裡 3 個是最佳實踐、3 個是「在約束下的正確務實選擇」，且每個 🟡 都有清楚的升級路。沒有一個是錯的。

## 4. 做得好的（值得保留的習慣）

1. **先量測再修，數據推翻假設**：地圖卡頓，Tony 原本猜是航線。實測發現元兇是**行政區邊界 GeoJSON（173,858 個頂點）**，航線只有 2,009 點，輕 86 倍。沒有量測就會修錯地方。
2. **原子 commit**：每個「驗證過、沒壞」的改動就 commit 一次，方便回溯，絕不 commit 壞掉的狀態。
3. **取代式改版當下就刪舊碼**：Google 版面重設計後，立刻清掉 ~250 行死 CSS（grep 確認 0 引用），不留垃圾。
4. **拒絕過度工程**：明確「沒做」清單——shadow/radius tokenize、per-section 內容檔、build-time generator，都因為「增加 indirection 但不是需求」而擋下。
5. **單一真實來源**：`app/config/site.ts` 同時餵 `app.config.ts` 和 Storybook；emoji font-stack 重複 4 次收成一個 token。

## 6. 工作模式怎麼演化的

從「一次給一個指令」進化成 **`你 ↔ 我（翻譯 + 指揮）↔ 背景工人隊`**，全程 async：

- **心理醫生式陪聊**：邊聊邊把想法、決定、進度記進 `.planning/BOARD.md`（駕駛艙）→ Tony 隨時看得到全貌 = 掌控節奏。
- **background-first**：非即時的實作一律走背景程序，主對話永不卡住。
- **crew 大小配合工作量**：大且可平行的工作才派整隊（先給看計畫）；一行指令不召喚艦隊。
- **GSD 術語翻白話**：phase / roadmap 這些字 Tony 永遠不用學，只管聊。

## 7. 還沒拍板的決定

1. **本地預簡化邊界檔 vs 留 jsdelivr CDN**：現況是 CDN 抓完前端即時簡化（成本只 9.4ms）。升級成本地檔可省手機下載 174k 點 + JSON.parse，但要 commit 資產檔 + 處理 CC-BY 授權。建議先用現況，實機測手感再說。
2. **內容 CMS Phase 2（blog 外框）**：blog 文章本來就在 WordPress，價值低；且「外框放哪」有真實分歧（新 `content/site/blogs.yml` vs 既有 `app/config/site.ts`）。不出 guess。
3. **若不採用 MapLibre GL**：要移除 `maplibre-gl` + `@maplibre/maplibre-gl-leaflet` 兩個 dev-only dep。

## 8. Architect 審查（opus subagent）

一位 opus 主任架構師獨立讀過 codebase + 本 retro，刻意當懷疑者挑「只是 done、還不是 best」的地方。

**判定：`best-of-done`**——在時間約束下交付了工程品質最高的版本。效能根治徹底（量測 → 診斷 → 簡化）、commit 原子、**沒有偷吃步、沒有技術債、沒有死碼/監聽器洩漏**（Leaflet 全在 `ClientOnly` 內、`onUnmounted` 清理齊全、dev-only debug 物件只在 `import.meta.dev` 掛載）。距「手術般精準」還差約 2–3% 的清掃。

**找到的「最後 2%」小削角（低風險、低收益，建議下一輪做）：**

| #   | 削角                                                         | 位置                                                                                                    | 修法                                                         |
| --- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 1   | Storybook 容器用了 raw 調色盤 `bg-gray-50`（6 處）           | `SearchModal.stories.ts:41`、`BackgroundDots.stories.ts:17/31/45`、`ScrollToTopButton.stories.ts:24/46` | 換成 `bg-ash-white` brand token                              |
| 2   | blog 文章頁圖片 `rounded-xl`（卡片專用 radius 用在內聯圖片） | `app/pages/blogs/[...slug].vue:107`                                                                     | 確認用途後改 `rounded-button`/`rounded-input`，或留小 radius |

## 9. 可讀性關卡（haiku 新人能不能讀懂）

我請一位 haiku subagent 扮「剛進來幾個月的菜鳥工程師」逐段讀本文，誠實標出讀不懂的地方——直接測試「新人不用人帶就能接手」這個目標。

**第一版結果（不及格）**：新人實際理解度只有 **30–40%**。最致命的是 §3 技術決策段——一口氣堆了 8 個沒定義的術語（預渲染、payload、code-split、chunk、Douglas-Peucker、vector tiles、dev-gated、rolldown），新人讀到這裡只能去 google 或問人，不是自己讀懂。§8 的 `best-of-done`、`偷吃步`、`技術債` 也卡。

**據此修訂**：

1. 在最前面加了**名詞速查表**，把 haiku 標的全部 8 個術語 + 其他常見詞，每個用一句白話定義——讀者碰到不懂的回去查一行就懂。
2. §2 的「重投影 352→74ms」補上基準說明（同台弱機、同樣放大操作）。
3. §8 的工程術語在速查表裡都查得到。

**第二版複驗（通過）**：同一個 haiku 新人配著速查表重讀，§3 與 §8 都判「能」，理解度從 **30–40% 跳到 75–85%**，總結「能不靠別人讀懂並接手」。密度問題從「讀到一半放棄」降到「回查一行繼續」。

> 這一段本身就是吃自己狗糧：retro 在講「plain English、新人可接手」，那它自己就得先通過新人關卡。
